## 1. Table Schema — `audit_logs`

| Column | Type (SQLAlchemy) | SQL Type | Nullable | Default | Notes |
|---|---|---|---|---|---|
| `id` | `String(36)` | `VARCHAR(36)` | No (PK) | — | Generated by `event_generator.generate_audit_id()` as `f"aud-{uuid.uuid4().hex[:8]}"` — an 12-character string (`"aud-"` + 8 hex chars), well within the 36-character column budget. Collision probability across 8 hex characters ($16^8 \approx 4.3 \times 10^9$ combinations) is not formally bounded by the application; no uniqueness retry logic exists, but no collision has structural likelihood of occurring within a single session's practical event volume. |
| `session_id` | `String(36)`, `ForeignKey("game_sessions.id", ondelete="CASCADE")` | `VARCHAR(36)` | No | — | In the current deployment this is always the literal string `"incidentzero-alpha"` (Document 01, § 5.2). |
| `timestamp` | `DateTime` | `DATETIME` | Yes* | `datetime.utcnow` (evaluated at INSERT time) | **See § 1.1 — this column's value is independently generated from, and will differ from, the `timestamp` field carried in the in-memory/broadcast JSON payload.** |
| `tick` | `Integer` | `INTEGER` | No | — | The authoritative sequencing key (Document 03, § 1, Control Objective 2); equals `SimulationEngine.current_tick` at the moment the event was logged. |
| `event_type` | `String(50)` | `VARCHAR(50)` | No | — | One of the eight enumerated values in § 2. Not a database-level `CHECK` or `ENUM` constraint — enforcement is purely by convention of which string literals appear in application code. |
| `actor` | `String(50)` | `VARCHAR(50)` | No | — | One of the five values enumerated in Document 03, § 1, Control Objective 2. Likewise not database-constrained. |
| `details_json` | `Text` | `TEXT` | No | — | A `json.dumps(...)`-serialized object; schema varies by `event_type` (§ 3). Never `NULL`; an event with no meaningful detail still serializes `{}` at minimum (no such case currently exists — every event type carries at least one field). |
| `compliance_flag` | `Boolean` | `BOOLEAN` | No | `True` | `True` = within policy; `False` = a regulatory or financial control breach. Full semantics in Document 03, § 1, Control Objective 3. |

\* The column itself permits `NULL` (no `nullable=False` is declared on `timestamp` in the model), but in practice every row receives a value from the column default, so no row in normal operation has a `NULL` timestamp.

### 1.1 Timestamp Duality — A Documented Discrepancy

Two distinct timestamp values exist for every audit event, and a reviewer correlating the live WebSocket/REST feed against the durable SQLite row must account for both:

1. **Wire/in-memory timestamp** (`entry["timestamp"]` in `build_audit_entry`, visible in `GET /api/audits`, `GET /api/session/state`, and every `TICK_BROADCAST`): generated as `datetime.now(timezone.utc).isoformat()` — a **timezone-aware** ISO-8601 string (e.g. `"2025-01-15T14:32:07.481203+00:00"`), computed once, in Python, at the moment `_log_audit_event` is invoked.
2. **Persisted column timestamp** (`audit_logs.timestamp` in SQLite): populated by the SQLAlchemy column's `default=datetime.utcnow` — a **naive** (no timezone offset) UTC datetime, computed independently by SQLAlchemy at `INSERT` execution time, which is a distinct Python `datetime.utcnow()` call occurring microseconds to milliseconds after the wire timestamp was generated.

**Audit implication:** the two values are correlated but not byte-identical, and the DB value carries no explicit UTC marker (it is conventionally UTC by virtue of `utcnow()`, but nothing in the schema enforces or labels that). Any downstream reconciliation process joining live-feed exports against direct SQL exports must treat `tick` (§ 1) as the authoritative correlation key, not `timestamp`.

### 1.2 Response Schema Note

A Pydantic response model, `AuditLogResponse` (`backend/app/schemas/audit.py`), is defined with fields `id, session_id, timestamp, tick, event_type, actor, details: Dict[str, Any], compliance_flag` and `model_config = ConfigDict(from_attributes=True)`. **This schema is not currently wired as a `response_model` on any FastAPI route** — `GET /api/audits` is declared with return type `List[Dict[str, Any]]` and returns the engine's raw in-memory dictionaries directly (which use the key `details`, already a parsed `dict`, not the ORM column name `details_json`). The Pydantic schema exists as a forward-compatible contract for a future typed API surface; it should not be assumed to be enforced at the current API boundary.

## 2. Enumerated Event Types (Complete and Closed Set)

| `event_type` | Trigger condition | Actor | `compliance_flag` | Frequency characteristic |
|---|---|---|---|---|
| `INCIDENT_RAISED` | Stochastic cascading-failure check succeeds for a healthy service (Document 02, § 2.3) | `AUTOMATED_MONITOR` | `True` | Zero to many per tick, throttled to at most 4 simultaneously active incidents |
| `INCIDENT_ACKNOWLEDGED` | `POST /api/incidents/{id}/acknowledge` succeeds against an `active` incident | `VP_OF_INFRA` | `True` | At most once per incident (an incident can only be acknowledged from `active`; a second call returns 404) |
| `RUNBOOK_EXECUTED` | `POST /api/mitigations/execute` succeeds | `VP_OF_INFRA` | `True` | Unbounded — no server-side cooldown (Document 04, § 2) |
| `PROACTIVE_REFACTOR_CYCLE` | 20 consecutive ticks elapse with zero active incidents, and `tech_debt > 0` | `PLATFORM_TEAM` | `True` | At most once every 20 ticks, only during sustained quiet periods |
| `UNATTENDED_ALERT_VIOLATION` | An `active` incident's `mtta_seconds >= 12` — re-evaluated and re-fired **every tick** thereafter until acknowledged or resolved | `AUDIT_SYSTEM` | `False` | Recurring per incident per tick — not a one-time event (Document 02, § 4.2) |
| `SLA_BREACH_EMERGENCY_SANCTION` | Cumulative SLA `< 99.00%` after tick 24, on the tick status first transitions into `breached` | `AUDIT_SYSTEM` | `False` | At most once per breach episode (status must first recover to `running` before it can fire again) |
| `BANKRUPTCY_LIQUIDATION` | `budget <= 0.0`, on the tick status first transitions into `bankrupted` | `BOARD_OF_DIRECTORS` | `False` | Exactly once per session (terminal state; the tick loop halts immediately after) |
| `MONTHLY_AUDIT_CYCLE_SURVIVED` | `current_tick >= 720` and `sla_percentage >= 99.00%`, on the tick status first transitions into `victory` | `AUDIT_SYSTEM` | `True` | Exactly once per session (terminal state; the tick loop halts immediately after) |

No other `event_type` string literal appears anywhere in `backend/app/`. This table is exhaustive as of the current codebase.

## 3. JSON Payload Schemas per Event Type

All payloads below are the exact keys and value types produced by their respective `_log_audit_event(...)` call, serialized into `details_json` via `json.dumps`. Numeric costs are Python `float`; all other scalars are as typed.

### 3.1 `INCIDENT_RAISED`

```json
{
  "service_id": "srv-payment",
  "severity": "P1_CRITICAL",
  "incident_id": "inc-a1b2c3"
}
```

| Field | Type | Description |
|---|---|---|
| `service_id` | string | Foreign reference to the affected service's `id`. |
| `severity` | string | `"P1_CRITICAL"` or `"P2_HIGH"` — deterministically derived from the service's `tier` (Document 02, § 2.3). |
| `incident_id` | string | The newly created incident's own `id`, redundant with the row's implicit association but included for self-contained readability of the ledger entry. |

### 3.2 `INCIDENT_ACKNOWLEDGED`

```json
{
  "incident_id": "inc-a1b2c3",
  "mtta_ticks": 7
}
```

| Field | Type | Description |
|---|---|---|
| `incident_id` | string | The acknowledged incident's `id`. |
| `mtta_ticks` | integer | The incident's `mtta_seconds` value at the exact moment of acknowledgment — the final, frozen MTTA measurement for this incident (Document 03, § 1, Control Objective 3). |

### 3.3 `RUNBOOK_EXECUTED`

```json
{
  "action": "Rollback Canary",
  "service_id": "srv-payment",
  "cost": 1800.0,
  "tech_debt_delta": -2,
  "resolved_incidents": 1
}
```

| Field | Type | Description |
|---|---|---|
| `action` | string | The runbook's human-readable `name` from `MITIGATION_CATALOG` (Document 04) — not the machine `action_id`. |
| `service_id` | string | The target service. |
| `cost` | float | Dollar amount deducted from `budget`. |
| `tech_debt_delta` | integer | Signed TDI adjustment applied (before the 0–100 clamp). |
| `resolved_incidents` | integer | Count of incidents against this `service_id` that transitioned to `resolved` as a side effect (0, 1, or — in principle, if multiple incidents were ever concurrently open against the same service — more than 1). |

### 3.4 `PROACTIVE_REFACTOR_CYCLE`

```json
{
  "tech_debt_after": 24
}
```

| Field | Type | Description |
|---|---|---|
| `tech_debt_after` | integer | The resulting `tech_debt` value immediately after the ambient 1-point relief was applied (i.e., already decremented). |

### 3.5 `UNATTENDED_ALERT_VIOLATION`

```json
{
  "incident_id": "inc-a1b2c3",
  "fine_amount": 4500.0
}
```

| Field | Type | Description |
|---|---|---|
| `incident_id` | string | The still-`active`, still-unacknowledged incident whose MTTA has crossed or continues past the 12-tick regulatory window. |
| `fine_amount` | float | Always the literal constant `formulas.UNATTENDED_BREACH_FINE` (\$4,500.00) — this field does not vary. |

### 3.6 `SLA_BREACH_EMERGENCY_SANCTION`

```json
{
  "sla_percentage": 98.42
}
```

| Field | Type | Description |
|---|---|---|
| `sla_percentage` | float | `sla_percentage` rounded to 2 decimal places at the exact tick the `breached` status was entered. |

### 3.7 `BANKRUPTCY_LIQUIDATION`

```json
{
  "final_tick": 231
}
```

| Field | Type | Description |
|---|---|---|
| `final_tick` | integer | The `current_tick` value at which `budget` first reached exactly `0.0`. |

### 3.8 `MONTHLY_AUDIT_CYCLE_SURVIVED`

```json
{
  "sla_percentage": 99.61
}
```

| Field | Type | Description |
|---|---|---|
| `sla_percentage` | float | `sla_percentage` rounded to 2 decimal places at the tick `current_tick >= 720` was first satisfied together with the SLA condition. |

## 4. Query Patterns Used Against This Table

The only application-code query against `audit_logs` beyond a full-table scan (`GET /api/audits`, served from the in-memory mirror rather than SQL) is inside `generate_postmortem` (`backend/app/api/v1/audits.py`), documented in full in Document 05:

```python
db.query(AuditLog)
  .filter(AuditLog.event_type == "RUNBOOK_EXECUTED")
  .filter(AuditLog.details_json.like(f'%"{incident.service_id}"%'))
  .order_by(AuditLog.tick.desc())
  .first()
```

This performs a substring (`LIKE`) match against the serialized `details_json` text column to locate the most recent runbook execution mentioning the incident's `service_id` anywhere in its JSON payload — a pragmatic but non-indexed approach that relies on `service_id` values (e.g. `"srv-payment"`) being sufficiently distinctive strings that a false-positive substring match against an unrelated JSON field is not a practical concern given the fixed five-service topology. No index exists on `details_json`; this query is a full sequential scan of the session's `RUNBOOK_EXECUTED` rows, which is acceptable at the data volumes a single simulation session produces but would not scale to a multi-session, long-retention deployment without either a proper relational join key or a dedicated index/materialized column.
